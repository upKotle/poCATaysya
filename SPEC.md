Разработай MVP Scenic Drive — веб-приложение для красивых
автомобильных поездок по Москве.

ЦЕЛЬ

Получить работающий локальный проект для личного тестирования
и публикации исходников на GitHub.

Главный сценарий:
«У меня есть около часа. Хочу выехать из выбранной точки,
проехать по красивым улицам и вернуться обратно».

Дополнительный сценарий:
«Хочу доехать из A в B красивым маршрутом и готов добавить
к обычной поездке до N минут».

Приоритет — работающая вертикальная версия, понятный код
и честное отображение ограничений.

1. ГРАНИЦЫ MVP

- Только автомобиль.
- Начальная территория — центр Москвы, примерно внутри ТТК.
- Территорию покрытия хранить в конфигурации.
- Выбор точек кликом по карте, без поиска адресов.
- Русскоязычный интерфейс, пригодный для мобильного браузера.
- Без регистрации, базы пользователей, ML, LLM и платежей.
- Без голосовой навигации и интеграции с внешними навигаторами.
- Без актуальных пробок и гарантий текущей доступности дорог.
- Не добавлять Kubernetes, очереди задач и микросервисы.

2. СТЕК

Backend:
- Python 3.12.
- FastAPI, Pydantic, httpx.
- Shapely/pyproj, если нужны для расчётов расстояний и пересечений.
- pytest.

Frontend:
- TypeScript + Vite.
- Leaflet.
- Обычный CSS, без тяжёлой UI-библиотеки.
- Без React, если для текущего интерфейса он не нужен.

Маршрутизация:
- OSRM с автомобильным профилем.
- Обращения к OSRM только через backend.
- URL маршрутизатора задаётся через OSRM_BASE_URL.
- Реализовать небольшой адаптер RoutingClient.
- Не писать собственный алгоритм автомобильной маршрутизации.

Данные:
- Каталог красивых участков в GeoJSON.
- Конфигурация города отдельно от алгоритма.
- База данных для MVP не нужна.

Зафиксировать совместимые версии зависимостей и lock-файлы.
Перед использованием API проверить актуальную официальную документацию.

3. ИНТЕРФЕЙС

Один экран: карта и панель параметров.

Режим «Покататься»:
- Старт кликом по карте.
- Желаемая продолжительность: 30, 45, 60 или 90 минут.
- Предпочтения: вода, архитектура, зелень.
- Кнопка «Построить поездку».

Режим «Из A в B»:
- Две точки кликом по карте.
- Дополнительное время: 5, 10, 15 или 20 минут.
- Те же предпочтения.
- Кнопка «Найти красивый маршрут».

Результат:
- До трёх действительно различающихся вариантов.
- Маршрут на карте.
- Расстояние и примерное время.
- Названия включённых красивых участков.
- Короткое объяснение выбора на основе данных.
- В A → B показать обычный маршрут и разницу во времени.
- Возможность переключаться между вариантами.
- Состояния загрузки, ошибки и отсутствия подходящих маршрутов.

Видимая подпись:
«Время рассчитано без актуальных пробок.
Это планировщик поездок, не навигатор».

Не показывать пользователю технические коэффициенты ранжирования.

4. КАТАЛОГ КРАСИВЫХ УЧАСТКОВ

Хранить именно дорожные участки, а не координаты памятников.

Для каждого участка:
- id;
- name;
- geometry: LineString;
- routing_anchors: упорядоченные точки на проезжей части;
- direction: допустимое направление обхода участка;
- оценки water, architecture, greenery от 0 до 1;
- короткое описание;
- source_url, если есть источник;
- verification_status: draft или reviewed;
- verified_at: дата или null.

Промежуточные точки нужны, чтобы маршрутизатор провёл поездку
по нужной дороге, а не просто рядом с достопримечательностью.

Для первого рабочего результата достаточно 5–10 участков.
Не задерживать запуск ради большого каталога.

При доступе к картографическим данным подготовить начальные участки.
Не выдумывать точные координаты, источники и факт проверки.
Непроверенные оценки и геометрию явно помечать как draft.
Добавить инструкцию, как вручную проверить и исправить участок.

Не считать близость к реке или зданию доказательством видимости
из автомобиля. Оценки первой версии — редакционная гипотеза.

5. АЛГОРИТМ «ПОКАТАТЬСЯ»

Не запрашивать маршрут start → start без промежуточных точек.

Генерация:
1. Выбрать доступные красивые участки вокруг старта.
2. Сформировать ограниченное число комбинаций из 1–3 участков.
3. Учитывать их расположение: выбирать разные направления
   от старта, чтобы уменьшить поездки туда-обратно.
4. Для комбинаций запросить автомобильные маршруты:
   start → anchors участков → start.
5. Проверить фактическую геометрию полученных маршрутов.
6. Отфильтровать слишком длинные и сильно повторяющиеся варианты.
7. Ранжировать оставшиеся и вернуть до трёх разных поездок.

Продолжительность:
- Целевой интервал по умолчанию: 80–110% выбранного времени.
- Отображать фактическую расчётную продолжительность.
- Если подходящих вариантов нет, сообщить об этом.
- Более далёкие по времени варианты можно предложить отдельно,
  явно обозначив, что они не укладываются в запрос.

Качество:
- Поощрять разнообразие красивых участков.
- Штрафовать повторное прохождение одной дороги.
- Не начислять повторно красоту за круги по одному участку.
- Не использовать только площадь контура как оценку качества.
- Не требовать идеальной петли: небольшой общий участок
  при выезде и возвращении допустим.

6. АЛГОРИТМ A → B

1. Получить базовый маршрут напрямую через OSRM.
2. Выбрать красивые участки вблизи разумного коридора A → B.
3. Построить кандидатов через 1–2 участка.
4. Рассчитать полную продолжительность каждого кандидата.
5. Исключить маршруты, превышающие:
   время базового маршрута + разрешённое дополнительное время.
6. Оценить красоту фактически пройденных участков.
7. Удалить почти одинаковые варианты.
8. Вернуть базовый маршрут и до двух красивых альтернатив.

Если улучшения не найдено — показать базовый маршрут
и честное сообщение. Не переименовывать одинаковые маршруты
в «быстрый», «сбалансированный» и «живописный».

7. ОЦЕНКА И СРАВНЕНИЕ МАРШРУТОВ

Ранжирование вынести в отдельный модуль.

Учитывать:
- длину фактического прохождения красивых участков;
- предпочтения пользователя;
- долю красивого пути;
- повторные участки;
- отклонение от желаемой продолжительности для круговой поездки.

Не считать посещение одной anchor-точки прохождением всего участка.
Проверять совпадение маршрута с линией участка с небольшим
пространственным допуском и, где возможно, направлением движения.

Расстояния и буферы считать в метрах, не в градусах.

Сходство маршрутов оценивать по общим участкам дороги или
по геометрии с допуском. Один и тот же путь в обратном направлении
тоже считать повторением для оценки разнообразия.

Конкретные веса и пороги оформить как понятные настройки.
В README объяснить формулу и ограничения эвристики.

8. API

GET /api/health
GET /api/scenic-segments
POST /api/routes/loop
POST /api/routes/point-to-point

Запрос круговой поездки:
- start: {lat, lon};
- target_duration_minutes;
- preferences;
- seed: необязательное число для воспроизводимости.

Запрос A → B:
- start и end;
- max_extra_minutes;
- preferences.

Ответ:
- routes;
- warnings;
- для A → B — baseline_duration_seconds.

Каждый маршрут:
- id;
- geometry в GeoJSON;
- distance_meters;
- duration_seconds;
- scenic_segment_ids;
- explanation;
- при необходимости — отклонение от целевого времени.

Проверять диапазоны координат, покрытие, допустимое время
и слишком близкие A/B.

Во внешнем GeoJSON использовать порядок [lon, lat].
На границе с Leaflet явно преобразовывать координаты.

9. НАДЁЖНОСТЬ И ЗАПУСК

- Ограничить количество кандидатов и запросов на построение.
- Начальный лимит: до 20 кандидатов, до 4 параллельных запросов.
- Добавить таймауты и общий бюджет времени запроса.
- Кэшировать повторные обращения в памяти с TTL.
- Обрабатывать недоступность OSRM и отсутствие автомобильного пути.
- Не заменять отсутствующий путь прямой линией.
- Отклонять слишком далёкую привязку выбранной точки к дороге.

Предусмотреть локальный OSRM:
- Docker Compose для backend, frontend и маршрутизатора.
- Отдельный документированный шаг подготовки OSM-данных.
- Закреплённая версия образа и совместимый pipeline подготовки.
- Небольшой extract, покрывающий рабочую зону с запасом.
- Большие .osm.pbf и подготовленные файлы исключить из Git.

Не делать публичный demo-сервер OSRM обязательной зависимостью.
Если предлагается внешний сервер для быстрого запуска,
проверить правила использования и указать ограничения.

Для карты указать источник тайлов и атрибуцию.
Проверить правила выбранного провайдера, не скачивать тайлы массово.

10. ТЕСТЫ

Основные тесты работают без внешней сети, через фикстуры RoutingClient.

Проверить:
- запрет превышения дополнительного времени в A → B;
- начало и завершение кругового маршрута возле старта;
- штраф за повторение дороги;
- удаление почти одинаковых вариантов;
- отсутствие повторного начисления красоты;
- anchor рядом с участком не означает прохождение участка;
- порядок lon/lat;
- отсутствие подходящих кандидатов;
- таймаут и ошибку маршрутизатора;
- некорректные координаты и выход за покрытие.

Реальный интеграционный тест с OSRM запускать отдельно.
Проверить frontend build и пройти основные сценарии в браузере.

12. ПОРЯДОК РАБОТЫ

Реализовывать по этапам:

Этап 1:
Карта → выбор A/B → backend → настоящий автомобильный маршрут.
Сначала добиться работы этой цепочки.

Этап 2:
Небольшой каталог участков → круговая поездка через них →
время, расстояние и линия маршрута на карте.
Это первый полезный результат.

Этап 3:
Оценка повторов, ранжирование, несколько разных круговых вариантов.

Этап 4:
Красивые альтернативы A → B с жёстким лимитом дополнительного времени.

Этап 5:
Обработка ошибок, тесты, Docker, CI, README и скриншот.

После каждого этапа запускать соответствующие проверки.
Не ограничиваться каркасом, планом или моковыми маршрутами.

Если сеть или окружение блокируют реальные данные:
продолжать независимую работу, явно описать блокер,
не выдавать демонстрационные данные за рабочую маршрутизацию.

В конце сообщить:
- что реализовано;
- какие проверки действительно пройдены;
- точные команды запуска;
- какие данные ещё требуют ручной проверки.
