# Каталог дорожных участков

`data/moscow/scenic_segments.geojson` — 27 реальных линий автомобильных дорог из OpenStreetMap. Это отдельные OSM ways, а не вся улица: название в интерфейсе дополнено словом «участок».

## Происхождение

Получены через официальный OSM API `GET /api/0.6/map` из семи небольших фрагментов центра Москвы. Исходная геометрия сохраняется без придумывания координат. Каждый объект содержит `source_url`, версию и timestamp OSM way; коллекция — время импорта, источник и лицензию. Данные © OpenStreetMap contributors, [ODbL](https://www.openstreetmap.org/copyright). При распространении производного каталога сохраняйте атрибуцию и условия ODbL. Код и оценки не меняют лицензию исходных дорожных данных.

Все 27 записей имеют `verification_status: draft` и `verified_at: null`. Получение данных из OSM не означает ручную проверку. Оценки water/architecture/greenery в `scripts/initial_segments.json` — первоначальная редакционная гипотеза, а не измеренная видимость из автомобиля. С этапа 3 эти черновые оценки используются в ранжировании с учётом предпочтений. Это не делает их проверенными; соответствующее предупреждение остаётся в результатах.

Каталог расширен на западные набережные, северные парковые улицы и архитектурные улицы центра/востока. Новые оценки имеют более выраженные категории как редакционная гипотеза, но не проверены с точки зрения водителя; исходные оценки первых 9 записей не подгонялись под запрос.

Направление взято из тега `oneway`: `forward` — в порядке координат, `both` — разрешён любой обход. Для `oneway=-1` импорт разворачивает линию. Это не проверка текущих временных ограничений, закрытий, знаков или полос движения. Отобраны highway primary/secondary/tertiary/residential; пешеходные дорожки и явно закрытые/private дороги импортёр отвергает.

Routing anchors вычислены на 2%, 50% и 98% длины линии в проекции EPSG:32637, а не поставлены на достопримечательностях. После этого переведены обратно в WGS84 `[lon, lat]`. Начало/конец слегка сдвинуты внутрь участка, чтобы реже привязываться к другой дороге на перекрёстке.

## Воспроизведение импорта

Из корня проекта, после установки зависимостей backend:

```sh
curl --fail 'https://api.openstreetmap.org/api/0.6/map?bbox=37.59,55.738,37.61,55.747' -o /tmp/scenic-west.osm
curl --fail 'https://api.openstreetmap.org/api/0.6/map?bbox=37.60,55.765,37.62,55.776' -o /tmp/scenic-north.osm
curl --fail 'https://api.openstreetmap.org/api/0.6/map?bbox=37.635,55.742,37.652,55.752' -o /tmp/scenic-east.osm
curl --fail 'https://api.openstreetmap.org/api/0.6/map?bbox=37.535,55.715,37.56,55.737' -o /tmp/scenic-more-west.osm
curl --fail 'https://api.openstreetmap.org/api/0.6/map?bbox=37.59,55.751,37.615,55.765' -o /tmp/scenic-more-center.osm
curl --fail 'https://api.openstreetmap.org/api/0.6/map?bbox=37.65,55.755,37.675,55.773' -o /tmp/scenic-more-east.osm
curl --fail 'https://api.openstreetmap.org/api/0.6/map?bbox=37.55,55.785,37.575,55.802' -o /tmp/scenic-more-park.osm
backend/.venv/bin/python scripts/import_osm_segments.py \
  /tmp/scenic-west.osm /tmp/scenic-north.osm /tmp/scenic-east.osm \
  /tmp/scenic-more-west.osm /tmp/scenic-more-center.osm /tmp/scenic-more-east.osm /tmp/scenic-more-park.osm \
  --output /tmp/scenic-segments.geojson
```

Импортёр использует список конкретных OSM way IDs из `scripts/initial_segments.json`. Если исходный way удалён/разделён, сначала обновите этот список по карте; импортёр завершится ошибкой вместо выдуманной замены. Для побайтового воспроизведения нужен тот же снимок OSM; актуальный API со временем меняется. Не скачивайте карту массово: для новых небольших выборок используйте Overpass или локальный extract. Большие исходные XML не нужны в Git.

Проверьте результат импорта, затем вручную перенесите исправленные записи в каталог. Повторный импорт сбрасывает статус в draft; не перезаписывайте уже проверенный каталог автоматически.

## Ручная проверка и исправление

1. Откройте `source_url` конкретного участка. Убедитесь, что это проезжая часть для автомобилей; проверьте направление, доступ, повороты и актуальные ограничения. При необходимости используйте свежие панорамы с учётом их условий использования или личный проезд пассажиром.
2. Сравните `geometry.coordinates` с дорогой. Если OSM way слишком короткий, обрезан или включает неподходящий кусок, выберите/соберите непрерывную линию из исходных дорожных данных. Сохраняйте точные ссылки на источники, не ставьте точки «примерно возле» здания или воды.
3. Проверьте 2–5 упорядоченных `routing_anchors` на той же проезжей части. В каталоге они в порядке `[lon, lat]`; API пользовательского старта использует `{lat, lon}`. Anchors должны покрывать минимум 80% длины линии. Для разделённой дороги храните направления отдельными записями.
4. Постройте тестовую поездку через участок с локальным OSRM. Убедитесь, что маршрут проходит нужную дорогу, а не параллельную улицу или противоположную сторону. Сравните синюю линию с пунктиром каталога.
5. Отдельно проверьте, что видно из автомобиля. Близость к реке/зданию не доказывает видимость. Исправьте оценки от 0 до 1 и краткое описание по наблюдениям, не обещайте вид, которого не проверяли.
6. Только после этих проверок установите `verification_status: reviewed` и фактическую дату `verified_at: YYYY-MM-DD`. Для непроверенной записи оставьте `draft` и `null`.
7. Из `backend` выполните `uv run --locked pytest`; перезапустите backend, чтобы перечитать каталог. Валидатор проверяет координаты, покрытие, уникальные ID, неразрывную простую LineString, длину от 50 м, порядок anchors и их расстояние до линии до 5 м.

Добавление: создайте GeoJSON Feature по образцу существующего, задайте уникальный id, name, description, geometry, routing_anchors, direction (`forward`/`both`), water/architecture/greenery, source_url и поля проверки. Если источника нет, не выдумывайте его: допустим `source_url: null`, но координаты должны происходить из доступных дорожных данных.

## Ограничения проверки прохождения

Backend переводит геометрию в EPSG:32637 (метры). Каждое ребро дорожного участка сравнивается с рёбрами маршрута: требуется совпадение по расстоянию до 25 м и направлению до 30° (для `both` разрешено обратное движение). Совпавшие кусочки линии объединяются, покрытие должно быть не меньше 80%. Плоские торцы буфера и проверка направления не дают засчитать поперечное касание или один anchor как целый участок. Повторные проезды не увеличивают зачтённую длину; при нескольких проходах проверяются все подходящие рёбра, а не только ближайшая первая проекция на маршрут.

Из покрытой длины берётся только уникальная дорога. Пересекающиеся/дублированные записи каталога не дают повторных баллов. Геометрическая эвристика не доказывает видимость, полосу, безопасность или актуальную доступность дороги. Очень близкая параллельная улица может попасть в допуск; разнесённые полосы одной дороги могут не совпасть. Формула ранжирования, повторы, пороги и удаление похожих поездок описаны в [README](../README.md#ранжирование-и-разнообразие).
